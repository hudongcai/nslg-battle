# 战报自动监听授权设计 v3

更新时间：2026-07-15

## 设计目标

本次调整的重点不是重做自动监听本身，而是把“本地助手如何关联账号”这件事做得更顺。

目标：

- 用户不再需要理解“链接码”。
- 保留 helper token 机制，保证安全和可控。
- 账号授权和项目监听任务分离。
- 本地助手只保存助手专用 token，不保存账号密码。
- 项目、目录、开始监听等信息由用户后续实际操作自动同步。

## 核心结论

本地助手关联账号时，只需要解决一件事：

> 这台电脑上的本地助手，被哪个账号授权了？

关联成功后，本地助手只需要保存：

```text
helperToken
helperClientId
deviceId
apiBase
```

项目监听任务不应该在账号关联阶段处理，而是在网页里选择项目、选择目录、点击开始监听时再创建或更新。

## 核心流程矩阵（只看监听部分）

监听核心流程只围绕一件事展开：

> 一张本地截图，从文件夹被发现，到进入待处理队列，再到 OCR 成功后进入正式战报和图库。

| 序号 | 流程节点 | 触发方 | 文件存储位置 | 存储流转 | 关键字段流转 | 过程表/正式表 | 状态变化 | 页面展示 |
|---:|---|---|---|---|---|---|---|---|
| 1 | 选择监听目录 | 网页 | 本地文件夹路径，不上传文件 | `folderPath` 保存到监听任务 | `userId`、`projectId`、`helperClientId`、`folderPath` | `ocr_watch_tasks` | `idle` | 显示监听目录、绑定设备 |
| 2 | 开始监听 | 网页 | 文件仍在本地目录 | 只更新监听任务状态，不移动文件 | `watchTaskId`、`status`、`lastHeartbeat` | `ocr_watch_tasks` | `idle` → `running` | 显示监听中 |
| 3 | 扫描文件夹 | 本地助手 | 本地文件夹 | 只读取文件列表，不改文件 | `imageName`、`fileSize`、`mtime`、`imageHash`（建议） | 暂不入库，或只上报心跳 | `running` | 显示助手在线、最近心跳 |
| 4 | 判断新图片 | 本地助手 + 后端 | 本地文件夹 + MySQL 已处理记录 | 对比队列和图库，避免重复入队 | `projectId`、`imageName`、`imageHash`、`helperClientId` | 查询 `ocr_pending_tasks`、`battle_gallery` | 未入队 / 可入队 | 待处理数不一定变化 |
| 5 | 图片进入待处理队列 | 本地助手上传，后端接收 | 图片从本地文件夹复制到 MySQL 过程表 | 本地文件保留；图片内容写入 `ocr_pending_tasks.image_base64` 或后续文件存储引用 | `userId`、`projectId`、`watchTaskId`、`imageName`、`imageHash`、`imageBase64`、`source=auto-watch` | 写入 `ocr_pending_tasks` | 新建 `pending` | 待处理数 +1，列表出现图片 |
| 6 | OCR 开始处理 | 后端 / OCR 执行器 | 图片仍在 `ocr_pending_tasks` | 从过程表读取图片，发送到 OCR 服务 | `taskId`、`imageBase64`、`labelConfig`、`heroNames`、`tacticNames`、`playerNames`、`allianceNames` | `ocr_pending_tasks` | `pending` → `processing` | 列表显示解析中 |
| 7 | OCR 返回结构化结果 | OCR 服务 | 暂存在后端内存 | OCR 原始结果映射为战报字段 | `leftPlayer`、`rightPlayer`、`result`、`created_at`、`generals`、`tactics`、`loss`、`troops`、`stars` | 尚未写正式表 | `processing` | 页面可继续显示解析中 |
| 8 | 写入正式战报 | 后端 | 正式数据写入 MySQL | 结构化字段从 OCR 结果写入 `battle_records` | `projectId`、`attacker_name`、`enemy_name`、`left_generals`、`right_generals`、`left_tactics`、`right_tactics`、兼容平铺字段 | `battle_records` | 仍为 `processing` | 战报底表准备刷新 |
| 9 | 写入战报图库 | 后端 | 图片从过程表复制到图库表 | `image_base64` 转为图片二进制，写入 `battle_gallery.image_data` | `projectId`、`battleId`、`originalName`、`fileSize`、`uploadedBy` | `battle_gallery` | 仍为 `processing` | 可查看原图 |
| 10 | 完成并释放过程数据 | 后端 | 正式表和图库保留；过程表可清理 | 成功任务标记完成；后续可删除大字段或定期清理 | `taskId`、`battleId`、`finishedAt`、`status=done` | 更新 `ocr_pending_tasks`，正式数据在 `battle_records` / `battle_gallery` | `processing` → `done` | 待处理数 -1，已处理数 +1，战报列表刷新 |
| 11 | OCR 失败 | 后端 | 图片仍在过程表，便于重试 | 不写正式战报，不写图库；保留错误原因 | `taskId`、`errorMessage`、`retryCount`、`status=failed` | 更新 `ocr_pending_tasks` | `processing` → `failed` | 失败数 +1，可重试 |
| 12 | 重试失败任务 | 网页 | 图片仍从过程表读取 | 不重新上传本地文件，直接复用过程表图片 | `taskId`、`status=pending`、`retryCount+1` | 更新 `ocr_pending_tasks` | `failed` → `pending` | 回到待处理列表 |

### 文件存储流转

| 阶段 | 文件在哪里 | 是否保留 | 说明 |
|---|---|---|---|
| 原始截图 | 用户本地监听目录 | 保留 | 本地助手只读取，不删除、不移动 |
| 待处理阶段 | `ocr_pending_tasks.image_base64`，或后续独立文件存储引用 | 临时保留 | 用于 OCR、失败重试、排查问题 |
| 解析成功后 | `battle_gallery.image_data` | 长期保留 | 正式图库，以 `battleId` 关联战报 |
| 正式战报 | `battle_records` | 长期保留 | 保存结构化战报字段，不保存原始 base64 |
| 清理阶段 | `ocr_pending_tasks` | 可清理 | `done` 任务可删除图片大字段或整条清理；`failed` 建议保留 |

### 字段流转

| 字段类别 | 来源 | 过程表字段 | 正式表字段 | 用途 |
|---|---|---|---|---|
| 账号 | 网页登录 / helper token | `user_id` | `created_by`、`uploaded_by` | 权限校验、积分扣减、记录归属 |
| 项目 | 网页当前项目 | `project_id` | `battle_records.project_id`、`battle_gallery.project_id` | 归属项目 |
| 监听任务 | `ocr_watch_tasks` | `helper_task_id` / `watch_task_id` | 不进入正式战报 | 统计监听任务进度 |
| 文件名 | 本地文件 | `image_name` | `battle_gallery.original_name` | 展示、排查、去重参考 |
| 文件指纹 | 本地助手计算，建议新增 | `image_hash` | 可选进入 `battle_gallery.image_hash` | 核心去重依据 |
| 图片内容 | 本地文件读取 | `image_base64` | `battle_gallery.image_data` | OCR 输入、原图回看 |
| OCR 配置 | 项目标注配置、字典 | `label_config` | 不直接进入正式表 | OCR 解析辅助 |
| OCR 结果 | OCR 服务 | 可选 `ocr_result_json` | `battle_records` 结构化字段 | 生成正式战报 |
| 任务状态 | 后端维护 | `status`、`error_message`、`retry_count` | 不进入正式表 | 队列展示和重试 |
| 时间 | 后端生成 | `created_at`、`started_at`、`finished_at` | `created_at`、`updated_at` | 展示、排序、追踪 |

## 用户体验

### 推荐流程

```text
本地助手启动
  ↓
显示：未关联账号
  ↓
用户点击：关联账号
  ↓
自动打开网页授权页
  ↓
用户登录网页账号
  ↓
点击：授权此电脑助手
  ↓
网页通知本地助手完成激活
  ↓
本地助手保存 helperToken
  ↓
显示：已关联账号
```

用户看到的是“授权此电脑助手”，不需要看到“链接码”。

### 兜底流程

保留链接码作为失败兜底：

- 浏览器无法访问 `127.0.0.1:9999`
- 本地助手未启动
- 杀毒软件或系统策略拦截本机请求
- 用户在另一台机器上手动配置助手

兜底时再显示：

```text
复制链接码到本地助手
```

但默认主流程不展示链接码。

## token 的定位

系统里有两类 token：

| 类型 | 使用者 | 用途 |
|---|---|---|
| 网页登录 token | 浏览器网页 | 证明当前网页用户已登录 |
| helper token | 本地助手 | 证明这台助手已被某个账号授权 |

不建议本地助手保存手机号和密码。

原因：

- 账号密码是总钥匙，泄露后风险太大。
- helper token 是助手专用凭证，可以单独撤销。
- 后端可以区分“网页操作”和“助手自动操作”。
- 本地助手只需要自动监听权限，不需要完整账号权限。

## 账号关联和任务绑定

### 账号关联

账号关联只处理：

```text
userId
deviceId
helperClientId
helperToken
apiBase
```

对应数据表：

```text
local_helper_clients
```

关键字段：

```text
id                 helperClientId
user_id            所属账号
device_id          本地设备标识
device_name        设备名
access_token       helperToken
status             online/offline
helper_version     助手版本
last_seen_at        最近活跃时间
```

### 项目监听任务

项目监听任务只在用户后续操作时处理：

```text
projectId
folderPath
helperClientId
status
pendingCount
processedCount
lastHeartbeat
```

对应数据表：

```text
ocr_watch_tasks
```

关系：

```text
一个账号可以有多个本地助手
一个项目监听任务绑定其中一台本地助手
```

## 推荐交互细节

### 本地助手界面

本地助手建议显示：

```text
账号状态：未关联 / 已关联
设备编号：#123
服务状态：运行中
监听状态：等待网页选择项目和目录

[关联账号]
[重新关联]
[打开网页]
```

本地助手不需要用户手动选择项目。

### 网页自动监听面板

网页面板建议显示：

```text
本地助手：已连接 / 未连接
账号授权：已完成 / 未完成
绑定设备：#123
监听目录：C:\...
任务状态：空闲 / 运行中 / 暂停 / 离线 / 错误
```

按钮逻辑：

- 未安装助手：显示“下载本地助手”
- 助手运行但未授权：显示“授权本地助手”
- 已授权但未选目录：显示“选择监听目录”
- 已选目录：显示“开始监听”

## 推荐接口

### 1. 网页发起助手授权

保留当前自动激活能力：

```text
POST http://127.0.0.1:9999/activate
```

请求：

```json
{
  "token": "网页登录 token",
  "apiBase": "https://api.zhenwu.fun/api"
}
```

本地助手收到后，向后端换取 helper token。

### 2. 后端发放 helper token

沿用当前接口：

```text
GET /api/ocr-watch/helper-config?deviceId=xxx
Authorization: Bearer 网页登录 token
```

返回：

```json
{
  "code": 200,
  "data": {
    "helperToken": "helper-auth-xxx",
    "helperClientId": 123,
    "apiBase": "https://api.zhenwu.fun/api",
    "userId": 1,
    "deviceId": "device-xxx"
  }
}
```

本地助手保存 `helperToken`，后续请求后端时使用：

```text
Authorization: Bearer helper-auth-xxx
```

### 3. 创建或更新监听任务

仍由网页触发：

```text
POST /api/ocr-watch/tasks
Authorization: Bearer 网页登录 token
```

请求：

```json
{
  "projectId": 10001,
  "folderPath": "C:\\AutoScreenshotTool2\\screenshots",
  "helperClientId": 123
}
```

含义：

> 当前网页用户，把这个项目的监听任务绑定到这台本地助手。

### 4. 本地助手拉任务

本地助手使用 helper token：

```text
GET /api/ocr-watch/tasks
Authorization: Bearer helper-auth-xxx
```

后端只返回属于该账号、且绑定到当前 helperClientId 的任务。

### 5. 本地助手上传 OCR

```text
POST /api/battles/ocr-upload
Authorization: Bearer helper-auth-xxx
```

自动监听上传必须使用 helper 身份，继续保留这条约束。

## 状态判断

### 助手是否在线

网页判断：

```text
GET http://127.0.0.1:9999/status
```

返回中关注：

```text
running
configured
helperClientId
folderExists
```

### 任务是否真的运行中

不能只看 `status = running`，还要看：

```text
lastHeartbeat 是否在有效时间内
```

推荐：

```text
30 秒内：认为正在工作
2 分钟以上：前端显示离线或未工作
```

## 改造建议

### 第一阶段：调整文案和体验

- 把“链接码”主文案改为“授权本地助手”。
- 默认走自动激活流程。
- 链接码入口降级为“手动关联”或“无法自动关联时使用”。
- 网页面板显示“账号授权状态”和“绑定设备”。

### 第二阶段：梳理本地助手界面

- 本地助手增加“关联账号”按钮。
- 点击后打开网页授权页。
- 授权完成后本地助手显示“已关联账号”。
- 不在本地助手里选择项目。

### 第三阶段：强化后端约束

- `/api/ocr-watch/tasks` 对 helper token 只返回绑定到该 helperClientId 的任务。
- `/api/battles/ocr-upload` 对 `source = auto-watch` 继续强制 helper 身份。
- 任务创建时必须校验 `helperClientId` 属于当前登录账号。
- 支持后续撤销某台本地助手的 token。

### 第四阶段：保留兜底

- 保留“生成链接码”功能，但不作为主流程。
- 链接码说明改成：手动关联码。
- 自动关联失败时再展示手动关联码。

## 不做的事

本轮设计不建议：

- 不让本地助手保存账号密码。
- 不在账号关联阶段绑定项目。
- 不让本地助手自己决定监听哪个项目。
- 不让 helper token 拥有完整网页登录权限。

## 最终理解

一句话：

> 账号授权解决“这台助手属于谁”；项目监听解决“这台助手现在帮哪个项目监听哪个目录”。

token 继续保留，但用户默认不需要理解它。用户只需要完成“授权此电脑助手”这个动作。
